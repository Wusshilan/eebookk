# 项目架构设计：网易云风格的 calibre 外壳

> 状态：设计稿 v0.1　｜　工作目录：`D:\bookopen`

---

## 1. 定位

**不是 calibre 的皮肤，是一个把 calibre 当引擎的书库管理器。**

- 面向分发（要发布给他人使用）
- 目标库规模：几百本
- 核心能力：**管库 · 转换 · 推送 Kindle**（不是"逛书+读书"）
- 视觉：参考网易云音乐 PC 端，但要长出自己的辨识度

## 3. 决定性技术发现

### 3.1 calibre 主程序运行时，`calibredb` 完全罢工

实测（calibre GUI 正在运行）：

```
$ calibredb list --with-library "C:\Users\...\Calibre 书库" --for-machine
exit=1
stderr: 另一个诸如 calibre-server.exe 实例的 calibre 程序或主程序正在运行……
        同一时间运行多个 calibre 程序对书库进行修改是一个糟糕的想法。
```

**哪怕只是 `list` 读取，也会被拒绝。** 现有的 `calibredb.exe` 拒绝服务。

如果照搬"只调 CLI，不碰数据库"的经典方案，用户一旦同时开着 calibre，本产品的整个界面就是死的。这条路线直接废弃。

### 3.2 `metadata.db` 在 calibre 运行时可以只读打开

```
sqlite3.connect("file:...metadata.db?mode=ro", uri=True)   # 成功
306 本书全量 join 查询：1 ms
```

**读取走直连数据库，稳定、即时、不依赖进程状态。**

### 3.3 `ebook-convert` 独立于书库，随时可用

```
$ ebook-convert --version
ebook-convert.exe (calibre 9.15.0)
```

转换不需要书库锁，calibre 开着也能用。**转换走 CLI。**

### 3.4 calibre 9 已经自带阅读进度

`last_read_positions` 表：`book, format, user, device, cfi, epoch, pos_frac`
当前 8 条记录，来源 `calibre-desktop-viewer`。

→ "继续阅读"不必从零造，直接读这张表即可。

## 4. 三条技术路线裁决

| 路线 | 裁决 | 理由 |
|---|---|---|
| Fork calibre 改 Qt | ❌ 否决 | 百万行 PyQt6、每周发版、GPLv3 传染、Qt 做不了网易云那套动效 |
| 只调 `calibredb` CLI | ❌ 否决 | calibre 一开就全废（见 3.1），且每次 1~2s 进程开销 |
| **直连 `metadata.db` + CLI 混合** | ✅ 采用 | 读即时（1ms）、写可控、转换独立 |

### 读写策略

**读（永远可用）**
- `mode=ro` + `PRAGMA query_only=ON` 打开 `metadata.db`
- 306 本全量查询 1ms → 启动即全量载入内存，无需增量/分页的后端复杂度
- 监听文件 mtime + calibre 进程状态，做轻量刷新

**写（需要独占）**
- 前置条件：`calibre.exe` 未运行（进程检测 + `metadata.db-journal` 存在性）
- 单事务直写 `books` / `*_link` / `data` 表，更新 `last_modified`
- **不自行维护 FTS**（calibre 的全文检索是插件层，另建一套会打架）
- 写前校验 schema 版本（读 `preferences` 表），版本不符则降级为只读模式
- calibre 正在运行时：UI 明确显示「编辑已锁定 · calibre 正在运行」，并提供一个"关闭 calibre 并解锁"按钮

**转换（永远可用）**
- 起 `ebook-convert` 子进程，并发上限 2~3（calibre 自己用 3 个 `calibre-parallel` worker）
- 进度不追求精确百分比：按「载入 → 转换 → 写出」阶段推进，避免解析脆弱的 verbose 输出

## 5. 架构分层

```
┌──────────────────────────────────────────────┐
│  表现层  Electron + React + TS + Vite        │
│  书库视图 / 整理台 / 详情页 / 底部常驻条       │
└───────────────────┬──────────────────────────┘
                    │ IPC (contextBridge, 类型安全)
┌───────────────────▼──────────────────────────┐
│  主进程  Node/TS                             │
│  ├ calibre-adapter   读 DB / 写 DB / 版本守卫  │
│  ├ index-store       自己的 SQLite（进度/书单） │
│  ├ cover-pipeline    缩略图 + 主色提取         │
│  ├ job-queue         转换队列 / 推送队列       │
│  └ device-bridge     Kindle USB / SMTP 推送    │
└───────────────────┬──────────────────────────┘
                    │ 子进程 / 文件
┌───────────────────▼──────────────────────────┐
│  引擎层  calibre（用户自行安装，不捆绑）        │
│  metadata.db · ebook-convert · ebook-viewer   │
└──────────────────────────────────────────────┘
```

### 两个数据库

| 库 | 位置 | 归属 | 内容 |
|---|---|---|---|
| `metadata.db` | calibre 书库 | calibre | 书目元数据（读为主，受限写） |
| `app.db` | `%APPDATA%\<产品名>\` | 本项目 | 阅读进度镜像、书单、任务记录、封面主色缓存、设置 |

**绝不把 calibre 的库结构复制一份当主数据**——会失去同步一致性。只做必要镜像。

## 6. 许可与分发（已定：MIT + 不捆绑 calibre）

这是"要发出去"带来的硬约束。

- **本项目代码：MIT**
- **calibre：独立程序，GPLv3，不由本项目分发**
- 通信方式：子进程 + 只读数据文件，属独立程序协作，非衍生作品
- 不做：不修改 calibre 源码、不 `import` 其 Python 包、不打包其二进制
- 首次启动引导：检测 calibre → 未安装则提供 `winget install calibre.calibre` 或跳官网
- README 明确声明依赖关系

> 这是 calibre 生态里被大量项目验证过的做法。风险最低、维护成本也最低——用户升级 calibre，我们自动受益。

## 7. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 外壳 | **Electron** | 本机已有 Node 24，零额外工具链；缺 Rust 是硬伤，Tauri 要装 MSVC 构建链 |
| 前端 | React 19 + TypeScript + Vite | — |
| 样式 | Tailwind CSS + CSS 变量（主题令牌） | 主色驱动的动态主题必需 |
| 动效 | Motion（Framer Motion） | 网易云那套转场/展开全靠它 |
| 虚拟滚动 | `@tanstack/react-virtual` | 306 本不急需，但为未来几千本留余量 |
| 本地库 | `better-sqlite3` | 同步 API，主进程用最省心 |
| 图像 | `sharp` | 缩略图 + 主色提取，比 canvas 快一个量级 |
| 打包 | electron-builder（NSIS） | 自动更新走 electron-updater |

**关于 Tauri**：产物能小到 5~10MB，长期方向更好。但本机无 Rust、无 MSVC 构建工具，装机成本是几个 GB 加管理员权限。**v1 用 Electron 快速验证产品，架构保持外壳可替换**（IPC 层抽象好，将来换 Tauri 只换壳不动业务）。

## 8. 信息架构：两副面孔，一套骨架

网易云是"轻、少、沉浸"，管库是"重、多、表格"——**这两者不能揉在一页里**。解法是并列两个面孔，用底部常驻条作为枢纽。

### 面孔 A：书架（网易云味）
- 封面主色渐进铺满背景，大圆角卡片
- 顶部 hero：最近在读 / 最近入库，大封面 + 进度
- 网格书库，按 `最近添加 / 作者 / 系列 / 书单` 切换
- 点击进入**详情页**：主色背景 + 大封面 + 简介 + 元数据 + 系列同组

### 面孔 B：整理台（工作台味）
密集表格，但配色仍走同一条主色系，不做成"另一个软件"。

队列式任务流，像网易云的「待下载」：
- 缺简介 232 · 缺标签 271 · 缺系列 278 · 水印标签 N
- 多选 → 批量编辑 / 批量抓元数据 / 批量转换
- 可排序列、可筛选、键盘操作

### 枢纽：底部常驻条
网易云是播放器。这里是**三态常驻条**：

| 状态 | 显示 |
|---|---|
| 转换中 | 书名 + 阶段进度 + 并发数 |
| 推送中 | 目标设备/邮箱 + 结果 |
| 阅读中 | 当前书 + `pos_frac` + 继续阅读 |

这是"像网易云"最关键的一笔，也恰好是最适合管库的形态。

## 9. 差异化功能（"自身特色"）

排序按"痛点 × 实现成本"：

1. **标签净化器** ⭐ 最贴你们这个库
   自动识别 `天浪书屋`、`汇书网`、`-SanQiu.mobi` 这类下载站水印标签、乱码标签、重复语义标签，一键清理或合并。别人的 calibre 都有这问题，没人做。

2. **书库健康度**
   给整个库打一个分（元数据完整度 / 封面覆盖率 / 格式统一度），列出"最该修的 10 本"。把 232 本缺简介这种绝望数字变成可推进的任务。

3. **系列补齐**
   检测系列断档（已有 6 个系列，`村上春树长篇小说修订版` 11 本、《六史》6 本、《龙族》5 本），提示缺哪几本。

4. **转换队列可视化**
   把 calibre 那个不可名状的 jobs 对话框，做成播放列表式的队列，带阶段、耗时、失败原因。

5. **Kindle 推送一等公民**
   每本书卡片上一个直推按钮，SMTP 自己实现（QQ/163 授权码），凭据用 Electron `safeStorage`（DPAPI）加密存本地；USB 连接时自动识别 `documents` + `system` 目录并提供拷贝。
   注意：Amazon 自 2022 起只收 EPUB/PDF/DOCX，**不要再转 MOBI/KFX**（会自己加页边距）。

6. **精排阅读模式**（后期）
   复用《脂评石头记》那套排版 CSS，做内置 Web 阅读器。calibre 自带 viewer 反而是这里最该被替换的部件。

## 11.5 实现期补充的实测结论（v0.2）

### 写入只能走 `calibredb`，不能直连数据库

实测 `metadata.db` 的 `books_update_trg` / `books_insert_trg` 触发器会调用
calibre 在 Python 侧注册的 SQL 函数：

```
sqlite3.OperationalError: no such function: title_sort
```

也就是说，直接用 SQL `update books set title=...` 会失败。要用直写路线，
必须把 calibre 的 `title_sort` / `author_to_author_sort` / `books_list_filter`
等一大票 UDF 全部用 JS 复刻一遍——语义（尤其中文排序）稍有偏差就会把库写脏。

**结论：写路径统一走 `calibredb set_metadata / remove / add`。**
代价是每次调用 1~2s 进程开销，写 20 本大约 20~40s，用队列 + 进度条吸收即可。

### `calibredb` 的锁是全局的，不认书库路径

即使 `--with-library` 指向一个完全独立的测试库，只要系统里有 calibre 进程在跑，
就照样报「另一个 calibre 程序正在运行」。所以：

- **编辑功能的前置条件是 calibre 完全退出**
- UI 常驻 `编辑已锁定` 状态（每 4s 轮询 `tasklist`）
- 提供「关闭 calibre」动作（`taskkill /IM calibre.exe` 不加 `/F`，发正常关闭信号）

### 转换可以并行，不需要书库锁

`ebook-convert` 与书库无关，calibre 开着也能跑。进度在 **stdout**：

```
1% 转换为HTML中...
34% 正在进行电子书转换...
67% 正在运行 MOBI Output 插件
```

必须加 `--verbose`。按行匹配 `/^(\d+)%\s+(.+)$/` 即可拿到百分比和阶段。
实测 100KB EPUB → MOBI 约 3 秒。

### 标签垃圾的判定要避开出版社名

第一版启发式把「商务印书馆」误判成下载站（因为规则里有「馆」后缀）。
最终收敛为四类特征，避免误伤「中华书局」「商务印书馆」这类正规出版社：

1. 明确的盗版源名：`z-lib` / `annas archive` / `sanqiu` / `天浪` / `汇书` / `雅书` …
2. 引流话术：`公众号` / `微信` / `qq群` / `扫码` / `免费分享` / `更多好书` …
3. 网址或文件格式：`www.` / `.com` / `.mobi` / `.epub` …
4. 短站点名：含「书/文/读」且以「网/屋/阁」结尾且 ≤6 字

—— **不再**用「店/局/城/社/馆」这类出版社会用到的字。
